# 번역 후보 탐색용 문단

후속 비교의 동결 개발 자료는 [언어학적 실행 원칙](LINGUISTIC_OPTIMIZATION_PROTOCOL.md)을 따른다. `linguistic-dev-20260910.jsonl` 18개와 `real-reading-check-20260910`의 실제 원문 6개는 아래의 옛 탐색 자료와 별개이며, 기존 최종 시험을 재사용하지 않는다. 실행 명령과 메모리 관리·원문 손상 제외 근거는 [비교 도구 안내](../../scripts/model-comparison/README.md)에 있다.

[finance-probe-20260909.jsonl](finance-probe-20260909.jsonl)은 2026-09-09 번역 후보의 실제 출력·속도를 비교하기 위해 도우미가 영어 본문과 한국어 참조를 **독립 작성한 미검수 탐색 자료**다. 실제 다모다란 원문의 인용·번역, 사용자 검수쌍, 전문 번역가 검수 자료가 아니다. 제목의 `독립 작성 예시`도 이를 표시한다.

모든 행은 `provenance: assistant_authored_unreviewed`, `split: exploratory_probe`다. 기존 train/dev/test 본문을 열거나 재활용하지 않고 새로 작성했다. 기존 분할과의 자동 근접 중복 검사를 실행했다는 뜻은 아니다. **최종 독립 시험이 아니며**, 모델 가중치 학습·최종 test 점수·앱 등록의 통과 근거에 합산하지 않는다. 이 자료로 후보를 비교하거나 개선 방향을 선택한 뒤에는 새로 분리하고 검수한 시험 자료가 필요하다.

금융 10개와 일반 2개로 구성한다. 금융 중 앞 6개는 공백 기준 45~75단어의 2~4문장 문단이고, 뒤 4개는 20~35단어의 짧은 설명이다. 가치와 가격, 성장과 재투자, 현금흐름과 할인율, 계속가치 수식, 운전자본, 레버리지, 실물옵션, 이자보상배율, 영업이익률과 자본수익률, 채권 듀레이션을 다룬다. 일반 사례는 지시 대상·조건·부정과 숫자 보존을 확인한다.

각 행의 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `id` | 비교 출력과 연결하는 고유 ID |
| `domain` | `finance` 또는 `general` |
| `title` | 독립 작성 예시임을 표시한 한국어 제목 |
| `provenance`, `split` | 작성 출처와 탐색용 용도 |
| `source` | 모델에 제공할 영어 본문 |
| `reference` | 도우미가 작성한 한국어 참조. 유일한 정답이나 사용자 검수본이 아님 |
| `expectedTerms` | `{source, acceptedTargets}` 배열. 표기 적중을 볼 수 있는 용어와 허용 표기 예시 |
| `criticalChecks` | 한국어로 적은 의미·조건·부정·지시 대상·숫자·수식 확인 포인트 |

비교 모델에는 `source`만 번역 입력으로 제공한다. 모델이 요구하는 언어 코드·고정 번역 템플릿은 각 실행 조건에 기록하되 `reference`, `expectedTerms`, `criticalChecks`를 정답 힌트로 주지 않는다. 같은 원문으로 생성하고 모델 revision·실제 가중치 해시·정밀도·장치·생성 설정·전체 입력·출력·시간·종료 상태를 보존한다. 모델이 달라 동일하게 적용할 수 없는 설정은 차이를 기록한다. 용어 보정이나 검수 번역 메모리를 쓴 결과는 원시 모델 출력과 구분한다.

표기 적중·숫자 보존·chrF·BLEU만으로 의미 품질을 판정하지 않는다. `acceptedTargets`는 허용 가능한 모든 번역을 열거하지 않으며, 표기가 일치해도 관계가 틀릴 수 있다. `criticalChecks`에 따라 누락·반전·잘못된 주어·조건·자연스러움을 함께 읽는다. 번역의 문장 수나 한국어 어순이 참조와 다르다는 이유만으로 실패 처리하지 않는다. 소수의 미검수 합성 사례에서 좋게 나온 결과를 전문 금융 번역 품질 보증으로 표시하지 않는다.

원문의 명시적 숫자와 수식 표기를 참조에도 보존했다. 숫자의 등장 순서는 한국어 어순에 맞게 달라질 수 있으므로 단순 순서 비교와 의미 관계 검토를 구분한다. 이 파일 추가는 운영 DB·개인 기록·원문 버전·앱 제공자·작업 큐를 변경하지 않으며 유료 API 호출을 실행하지 않는다.

작성 후 Python 표준 라이브러리로 JSON 파싱·필수 필드·ID 고유성·영역별 개수·문장 및 단어 수 범위·용어 출현·숫자 다중집합·수식 보존을 확인했다. 긴 금융 문단의 공백 기준 단어 수는 순서대로 57, 61, 62, 68, 66, 68이며 각각 3문장이다. 짧은 금융 사례는 26, 30, 29, 30단어이고 일반 사례는 43, 41단어다. 이 검사는 데이터 형식 확인이며 앱 테스트나 실제 번역 엔진 품질 검증이 아니다.
