사용자의 “그냥 지금 시작하면 안됨?” 요청을 반영해 [별도 메모리 정책](LOCAL_QUESTION_MEMORY_EXECUTION_V6.md)을 추가했다. 도우미가 과거 peak working set 약5.246GiB를 근거로 시작 physical만9→7GiB로 조정했다. commit9GiB·모델 관측 상한6GiB·실행 중 여유1GiB·전원/시간/소유 종료 보호와 모델·입력·생성·품질 기준은 유지한다. 시스템 전체 메모리 변동 때문에 완료는 보장하지 않는다.

새 native/context·runner 합성31개, 수집/평가/원장 합성19개와 추가 정체성 변조 검사, private 채점 컨트롤러 합성8개를 통과했다. 08:59:36 KST 직전 관측에서 가용 physical8,988,819,456바이트(8.37GiB), commit13,570,895,872바이트, AC1·배터리100%, 분류된 모델/worker 경합0개였다. 아래 실제 run 명령을 시작했으며 최초 기존 증거/모델 파일 검증 후 현재 자원을 다시 관측한다. 명령 시작을 전체 생성 완료로 세지 않는다. 실행 중 동결 코드나 질문을 수정하지 않는다.

## 사용자 요청에 따른 캐시 정리

사용자는 불필요한 메모리·캐시를 그때그때 정리하도록 추가 지시했다. 실제 프로세스를 확인했을 때 저장소 소유 Python·모델·worker·고아 검증 보조 프로세스가 없어 종료한 프로세스는 0개다. 다른 대화 런타임·사용자 브라우저·에디터·OS 프로세스를 임의 종료하지 않았다.

재생성 가능한 `.next/dev/cache/webpack` 10개 파일, `scripts/`의 6개 `__pycache__` 폴더 안 65개 파일, `.training/datasets/finance-v4/__pycache__`의 1개 파일을 확인했다. 모두 저장소 내부·Git 미추적·reparse point 없음, Python 원본 존재를 확인했으며 관련 증거 metadata 923개에서 해당 캐시 참조는 발견하지 못했다. 폴더 재귀 삭제 명령은 자동 승인 검토의 `blocked by policy`로 실행 전에 거부됐다. 이후 이미 확인한 **개별 파일의 절대 경로만 지정한 비재귀 삭제**를 실행해 76파일·62,740,928바이트(약 59.83MiB)를 정리했다. 캐시 폴더 자체, `.rscinfo`, devtools 설정과 production `BUILD_ID`는 유지했다. 삭제 파일은 백업하지 않았으나 필요한 실행·빌드 시 원본에서 재생성할 수 있다.

[정리 영수증](../../../.training/verifications/question-resume-cache-cleanup-20260920.json)은 삭제 범위와 후속 확인을 기록한다. 08:44:51~54 KST 두 관측의 가용 RAM은 7.228·7.250GiB로 여전히 시작 조건에 미달했다. 디스크 59.83MiB 정리를 RAM 확보 성과로 계산하지 않는다. 새 run/claim은 아직 없고 새 질문 호출도 0회다. 작업 중 Python은 `-B`로 실행해 불필요한 bytecode 캐시 생성을 억제하며, 이후에도 작업 소유 프로세스와 재생성 가능한 캐시만 점검한다. 원문·DB·학습 가중치·체크포인트·optimizer·평가 증거와 기존 9개 답변은 보존했다.
