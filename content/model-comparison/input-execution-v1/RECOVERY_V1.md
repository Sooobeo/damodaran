# S4 전원 중단 복구 계약 v1

2026-09-13의 사용자 지시(S4부터 나머지 진행)와 S1 CONTRACT 8절의 기술 실패 복구 규칙에 따른다. 최초 실행의 품질 결과를 바꾸는 재생성은 허용하지 않는다.

원래 `s4-generation/attempt-001`은 38/64 출력 저장, 39회 요청 후 `IP1-G02/C2`에서 실패했다. 마지막 요청은 응답 바이트 없이 ConnectionResetError를 기록했고 자원 감시의 중단 원인은 `ac_power_lost_or_unknown`이다. 실패 요약, 원시 HTTP, 26개 미완료, 소유 종료와 전원 요청 해제를 보존한다. 시스템 절전·수동 동작이 정확히 언제 어떤 영향을 줬는지는 이 증거만으로 확정하지 않는다.

새 실행은 `s4-recovery/recovery-attempt-NNN`에만 기록한다. 원래 38개를 원시 응답·입력·설정·파일 해시로 검증하고, 같은 고정 순서의 나머지 26개만 한 번씩 호출한다. 중단된 39번째 요청이 서버에서 어느 단계까지 처리됐는지는 알 수 없으므로 새로운 26개 중 첫 호출을 기술 복구 재요청으로 명시한다. 정상 완료 38개의 번역, 줄바꿈, run ID와 producer 버전을 바꾸거나 품질에 따라 교체하지 않는다.

모델, 가중치, 등록, 런타임, 샘플링, 원문, 문맥, 사전, Jinja, tokenizer, 자원 제한은 최초 실행과 같다. 원래 S1~S4 및 평가 동결 파일은 수정하지 않는다. 새 producer·검증 코드와 이 계약은 새 실행 plan의 해시 입력에 포함한다. 새 런타임에서 64개 전체 template/token 대조 후에만 미완료 26개를 호출한다. AC1과 기존 자원 사전검사, 소유 프로세스 종료, 강제 종료·자원 감시 조건을 다시 충족해야 한다.

복구 요청을 하나라도 보낸 뒤 같은 복구 producer를 자동 재실행하지 않는다. 다시 실패하면 새 기술 복구 계약과 정체성이 필요하다. 대기 시간 경과를 전원 연결 또는 실행 조건 충족으로 간주하지 않는다.

성공 시에도 원래 실행을 성공으로 고치지 않는다. 별도 cohort manifest가 원래 실패 실행의 38개와 새 실행의 26개를 연결한다. 예상 총계는 65회 요청(원래39 + 새26), 완료64개, 응답을 확보하지 못한 원래 요청1회이다. 각 출력의 실제 런·원시 증거를 보존하고 논리 비교 묶음의 완결성과 단일 실행 성공을 구분한다. 아직 성공하지 않은 복구를 완료로 미리 기록하지 않는다.

S5는 별도 recovery 평가 경로에서 전체 64개와 두 실행 증거를 검증한 뒤 진행한다. 질문 packet, 익명 순서, 핵심 명제·용어·원문 대조·독립 질문 조건과 후보 기준은 그대로다. 38개 중 작성해 둔 원문 대조 초안은 새 정식 source packet과 바이트 동일성 및 근거 보존을 확인한 뒤 검토자가 확인해야 한다. 질문 응답은 새 독립 context에서 수행하며 root가 대신 답하지 않는다. S6는 기존 조건에 따라 후보가 있을 때만 확대한다.

이번 복구는 앱 등록, 운영 DB, 모델 가중치, 유료 호출을 변경하지 않는다. 조건부 S6의 앱 적용은 기존 수용 기준과 별도 실제 앱 검증을 모두 통과한 경우에만 진행한다.
